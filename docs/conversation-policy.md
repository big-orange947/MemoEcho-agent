# 会话值守 / 监视 / 上报

本文档说明 Memo Echo v2 的**会话级策略**:谁能自动回复、谁只被静默记录、重要消息如何上报给上游。

设计目标:默认什么都不做(不记录、不回复、不上报),由人显式按会话开启。

---

## 1. 三个开关

策略存在 `conversations` 表上,每个会话一行。**默认全关**。

| 开关 | 取值 | 默认 | 含义 |
|---|---|---|---|
| `monitor` | 0/1 | 0 | **总开关**。关闭 ⇒ 该会话的消息不落库、不写记忆、不上报、不回复 |
| `reply_mode` | off / draft / auto | off | off 不回复；draft 生成回复但**不发出**，存成待确认草稿；auto 自动回复 |
| `alert_enabled` | 0/1 | 0 | 命中"重要消息"规则时投进上报队列 |

**蕴含关系**:`reply_mode≠off` 或 `alert_enabled=1` ⇒ 自动打开 `monitor`(不监视就没有数据)。
API 会在返回值里用 `implied` 字段明确告知"顺手打开了哪个开关",不静默改语义。

其余可调项:

| 字段 | 默认 | 说明 |
|---|---|---|
| `persona` | 空 | 会话人设 / **值守注意事项**(如"别答应晚上十点后的活动"),注入系统提示 |
| `alert_keywords` | `[]` | 上报关键词(如 `["急事","改时间"]`) |
| `require_human_confirmation` | 1 | 拿不准时是否必须请示号主。**默认开**；显式关掉后 agent 在目标范围内自主决定（少来回问），但**底线约束不变**（不越界承诺 / 不编造 / 不替号主拍板）—— 关掉只是"少问"，不是"胆子变大" |
| `digest_window_seconds` | 1800 | 攒批记忆:消息静止多久触发总结 |
| `digest_max_messages` | 20 | 攒批记忆:攒够多少条触发总结 |
| `allowed_tools` | `[]` | 工具授权;空 = 按会话类型取默认(群聊默认不给 `send_qq_message`) |

## 2. 怎么配置

### 2.1 命令行(人直接操作,推荐日常使用)

```powershell
# 看所有会话及其开关
uv run python scripts/set_policy.py list

# 只监视不回复(静默收集)
uv run python scripts/set_policy.py set --qq 2597164807 --monitor

# 开启自动回复 + 注意事项
uv run python scripts/set_policy.py set --qq 2597164807 --reply auto --note "别答应晚上十点后的活动"

# 群聊: 监视 + 上报 + 关键词
uv run python scripts/set_policy.py set --group 123456 --monitor --alert --keywords 急事,改时间

# 一键回到静默
uv run python scripts/set_policy.py set --qq 2597164807 --off
```

### 2.2 HTTP API(前端 / 上游主 agent)

```http
# 按三元组定位(或创建)会话 —— 默认全关的会话没有消息,只能这样找到它
POST /api/conversations/resolve
{"platform":"qq","chat_type":"private","external_id":"2597164807","title":"小号"}

# 修改配置
PATCH /api/conversations/{id}
{"reply_mode":"auto","persona":"别答应晚上十点后的活动"}
→ {"conversation":{...}, "changed":{"reply_mode":["off","auto"]}, "implied":["monitor"]}
```

### 2.3 主 agent 派发(自然语言配置)

主 agent 听到"开始自动回复与 XXX 的会话,注意事项是别提钱"后,翻译成一次 dispatch:

```http
POST /api/dispatch
{
  "caller": "main-agent",
  "kind": "configure",
  "target": {"platform":"qq","chat_type":"private","external_id":"2597164807"},
  "policy": {"reply_mode":"auto","note":"别提钱"}
}
```

`kind=configure` **不产生任何对外消息**,只改配置 + 写审计 + 推送 SSE。
`note` 是 `persona` 的别名,两个都接受。

## 3. 消息怎么被处理(分流规则)

**权威规则:显式指令 > 会话策略。** 人明确要求做的事,不受开关约束。

| 事件来源 | 是否受策略约束 |
|---|---|
| 主 agent 派发(task / handle_message) | **不受** |
| 桌面端 / 前端指令、定时唤醒(有活动目标时) | **不受** |
| QQ 对方发来的消息、群聊消息 | 受 |
| 号主手机自己发的消息(message_sent) | 受(监视时记录,永不回复) |

| monitor | reply_mode | 对方消息 | 自发消息 | 群未 @ |
|---|---|---|---|---|
| 0 | – | 仅审计 | 仅审计 | 仅审计 |
| 1 | off | 落库 + 报道评估 | 落库 | 落库 |
| 1 | auto | 落库 + 回复 | 落库 | 落库 |
| 1 | draft | 落库 + 生成回复但**不发出**(存成待确认草稿) | 落库 | 落库 |

### 3.1 草稿模式(draft)

`draft` 与 `auto` **一样跑图**(否则没有草稿可看),区别只在最后发不发:
产出的回复进上报队列的 `draft` 通道等号主确认,对方**完全收不到**。

几条刻意的设计:

- **草稿不进对话历史**(不作为 assistant 消息落库)—— 对方确实没收到,
  记进去会让下一轮的模型以为自己已经说过了;
- **同一会话只保留最新一条未处理草稿**: 对方再发一句,旧草稿就已过时,
  留着只会让号主在一堆过期版本里挑;
- **目标不会被草稿推进**: 模型可能以为说定了,但消息还躺在队列里 ——
  这时候把任务标成"完成"就是骗自己(与 HITL 的假承诺同一类问题);
- **显式指令不受草稿约束**: 主 agent 派发 / 桌面端命令是"人当场要求做的事",
  再套一层确认等于把命令降级成建议;
- **任务授权态不豁免草稿**: 授权态管"要不要参与",草稿管"发之前给不给我看" ——
  后者是安全阀,不会被前者掀开;
- **上报出口(sink)永不转发草稿**: 它是"还没发出去的话",不是通知。

确认与丢弃(见 §4.2 的接口;`scripts/drafts.py` 是命令行入口):

```powershell
uv run python scripts/drafts.py list                 # 看有哪些草稿
uv run python scripts/drafts.py show <id>            # 看全文
uv run python scripts/drafts.py send <id>            # 原样发出
uv run python scripts/drafts.py send <id> --text "八点半行吗?"   # 改一改再发
uv run python scripts/drafts.py drop <id> --reason "太生硬"      # 不发,留记录
```

**发送失败时草稿保持待处理**,便于重试;失败也不会在历史里留下"我说过"的记录。

**任务授权态**:显式指令在某会话建了目标(goal)之后,该会话在任务结束前可自由交流
—— 否则"帮我约 km 打游戏"在未开启自动回复的会话里根本推进不下去。
目标完成/放弃即恢复静默。

## 4. 重要消息怎么上报

发现是一条**四段流水线**,前两段是纯代码、零模型成本 —— 因为它们要对
监视中的**每一条**消息全量跑(监视是异步的,多几段判断不影响响应速度)。

```
消息 → ①信号提取 → ②事件判定 → ③上下文补强 → ④可选:快模型复核 → 队列
       (纯字符串)   (组合规则)   (查库/聚类)     (可关,预算封顶)
```

### 4.0.1 ① 信号提取(`app/signals.py`)

把消息拆成结构化信号,不下结论:

- **时间**: 中文时间表达 → 具体日期/时刻,并算出"离现在还有多久"。
  认"明天/下周三/9月12号/今晚/七点半/月底/截止/几点"这些说法,
  以及"有一点事"这类不是时间的假命中;
- **动作**: 变更(改到/取消/不去了)、事务(组会/面试/交材料)、金钱、
  请求、邀约、紧急、承诺、**抑制**(没事了/不用管)、疑问;
- **形态**: 有没有图/文件/语音、是不是只有个表情、是不是引用回复;
- **位置与量**: 命中词的位置(供组合判断相邻)、金额。

### 4.0.2 ② 事件判定(`app/event_rules.py`)

拿信号判"有没有值得号主知道的事",给**事件类型 + 分数 + 建议通道**。
关键是**组合规则**,单个关键词不算数:

| 规则 | 例子 | 结果 |
|---|---|---|
| 变更 + 具体时间 | "明天组会改到四点" | schedule_change,0.93 |
| 变更(无时间) | "那事改一下吧" | schedule_change,0.55 |
| 时间安排(无动词) | "明天下午三点见" | time_plan,0.60 |
| 截止 + 具体时间 | "材料周五截止" | deadline,1.0 |
| 模糊期限 | "月底前交" | deadline,0.75(不紧急) |
| 连发未回 | 4 条"在吗" | burst,0.70 |
| 纯闲聊 | "哈哈哈""改天再聊" | 不入队 |

另外两条闸门:

- **紧急要有理由**: 分数高不等于要立刻打扰人。要进 `urgent`,必须有
  "为什么是现在"——时间临近(3 小时内/今天)、明确说了急、或截止就在今天。
  否则"10月8号的活动改到9号"这种几周后的事只会进 normal;
- **抑制不否决**: "不用管了/已解决"降分,但不一票否决 ——
  误杀一条真事的代价,远大于多看一条废话。

阈值: `≥0.80 urgent`、`≥0.55 normal`、`≥0.40 digest`、`<0.40 不入队`。

### 4.0.3 ③ 上下文补强(在 `app/reports.py`)

- **连发未回**: 对方在本会话连发几条、期间我们一条没回 → 提权
  (一条"在吗"不算什么,四条就是有人在等回话);
- **与进行中目标相关**: 撞上正在推进的任务 → 提权;
- **同类事件聚类**: 窗口内(15 分钟)同一会话的**同类**事件合并成一条。
  群里"改到四点了""那改成四点吧""四点行"往往是一件事,不该报三条;
- **高置信直通**: 分数 ≥0.9 且判为 urgent 时**不等模型复核**,直接可消费 ——
  省一次调用,也省掉攒批的延迟(排期变更早一分钟知道有意义);
- **时间推进**: 后台每一轮都按当前时间重新评估在队记录 ——
  事情临近了(2 小时内)自己升级为 urgent,已经过去了打 `stale` 标记。
  静态规则只能在消息到达那一刻判一次,这一条是靠异步换来的。

### 4.0.4 ④ 快模型复核(可选)

把一批候选合并成**一次**调用,判 `urgent` / `normal` / `digest` + 一句话摘要。

- `MEMO_ECHO_ALERT_REVIEW_ENABLED=false` 可**完全关掉** ——
  判定层自己就能挑出排期变更/截止/金钱这类事件,复核只是最后一道过滤;
- 日配额 `alert_llm_daily_budget`(默认 200 次/天)封顶;
- **配额耗尽或复核失败 → 沿用判定层的通道**(不再一律降级为 normal)。
  原则:宁可多报一条,也不能漏掉急事。

### 4.0.5 已知边界

- **词表是中文口语导向的**: 英文/方言表达覆盖有限;
- **相对时间靠当前时刻推算**: "下周三"在不同时间点解析结果不同
  (这是对的,但也意味着历史消息的解析结果会随时间过期);
- **聚类按事件类型**: 同一件事被拆成不同类型(如"取消"+"改期")时不会合并;
- 判定层给出的是**建议通道**,最终仍可被复核修正或被上游 drop。

### 4.1 上报送到哪里(sink)

上报的**出口**由配置决定,默认只入队(等上游来取):

| 配置 | 行为 |
|---|---|
| `MEMO_ECHO_ALERT_SINKS=db`(默认) | 只入队。上游 agent 用下面的接口来取 |
| `MEMO_ECHO_ALERT_SINKS=db,qq` | **额外转发到指定 QQ 会话**(本机自闭环,不依赖上游) |

启用 qq 出口时还要指定转发目标:

```powershell
# 转发到自己的另一个号
$env:MEMO_ECHO_ALERT_FORWARD_TARGET = "private:1234567"
# 或转发到专用通知群
$env:MEMO_ECHO_ALERT_FORWARD_TARGET = "group:987654321"
# 单会话每小时最多主动报几条(不加急的;急事与请示不受限,默认 10)
$env:MEMO_ECHO_ALERT_MAX_PER_HOUR = "10"
```

**关键语义: 启用 qq 出口后,本地就是队列的消费者** ——
记录被本地认领并投递,上游就取不到了。这是刻意的:
否则同一件事会被报两遍(本地一条、上游一条)。要交给上游,把 `alert_sinks` 改回 `db` 即可。

通知的样子(急事与请示单独成条,普通消息合并摘要,防刷屏):

```
【急】km
对方七点要走，问今晚是否还来
原话: 你今晚还来不来？我七点就得走了
命中: urgent_word:急、time_soon:今晚七点

【待查看 · 3 条】
1. 班群 · 张三
   明天组会改到四点
2. 辅导员
   奖学金材料周五截止
```

通知里的"命中"就是判定层的证据(事件类型、为什么判急),排障时能直接看到
"这条为什么会报/为什么没报"。

### 4.2 上游怎么消费(类消息中间件)

```http
# 认领一批(带租约;幂等,至少一次投递)
POST /api/reports/claim
{"limit":10, "lane":"urgent", "lease_seconds":120, "claimed_by":"main-agent"}
→ {"items":[{"id":"...","lane":"urgent","payload":{"summary":"..."},"attempts":1}], "count":1}

# 处理完确认(或决定不报)
POST /api/reports/{id}/ack
POST /api/reports/{id}/drop   {"reason":"不重要"}

# 长轮询: 挂起等新消息(拿不到就等,拿到立刻返回)
GET /api/reports/subscribe?timeout=25

# 查看队列 / 统计
GET /api/reports?status=pending
GET /api/reports/stats
```

队列语义(对齐真 MQ):

- **至少一次**:认领带租约,到期未 ack 自动回队列重新投递;
- **死信**:认领超过 5 次进 `dead`,可查可重放;
- **幂等**:同一消息重复处理不会重复入队;
- **TTL**:已处理的记录超期自动清理。

lane 含义:

| lane | 用途 |
|---|---|
| `urgent` | 立即上报(模型判断时间敏感) |
| `normal` | 重要但不紧急 |
| `question` | **HITL 请示**:agent 拿不准,回来问号主;也用于**记忆冲突**(见 §6.2) |
| `digest` | 攒起来一起看 |
| `draft` | **待确认草稿**(`reply_mode=draft`):拟好的回复,等号主确认后才发 |

`draft` 通道有两个特殊之处,都不是"风格问题"而是硬约束:

1. **上报出口(sink)不认领它** —— 草稿是"还没说出去的话",转发出去等于
   既打扰了人、又把这条草稿消耗掉了,真正想发的时候反而没了;
2. **多一个出口**:`POST /api/reports/{id}/send` 会真的以号主身份发出消息
   (走 outbox:先落库再发送;失败不标记完成,可重试)。这是全系统唯一由人
   触发的外发入口,所以**只对 `draft` 开放** —— 别变成万能外发按钮。
   丢弃用既有的 `/drop`。

将来接入真 MQ(RocketMQ/RabbitMQ/Kafka)时,替换的是 sink 实现,
`report_queue` 的 claim/ack 语义可原样映射,业务代码不用改。

## 5. 人工介入(HITL)

**默认开启**(新会话 `require_human_confirmation=1`):用自然语言从主控台下命令时,
不需要额外配置就是 HITL 模式。显式关掉后,agent 在目标范围内自主决定(少来回问),
但提示词里那段**底线约束任何情况下都在**。

agent 替号主交涉时,遇到**只有号主能拍板**的事(对方改期、涉及承诺/钱/对外形象、
需要号主才知道的现实信息),会调用 `escalate_to_owner` 工具:

- 问题进上报队列的 `question` 通道(与重要消息同一出口);
- 目标进度标记为"等待号主指示"(桌面端进度卡可见),**仍是进行中**,不会被丢掉;
- **本轮不再回复对方**:请示的语义就是"停下等答复"。这道闸由代码保证
  (`act` 置 `awaiting_owner` → `finalize` 跳过发送),不只是提示词里的要求 ——
  否则工具返回后模型顺手写一句"我先问一下"就发给对方了;
- 没发出去的回复**也不会记进历史**(否则 agent 会以为自己已经说过了);
- 标记是"本轮"属性,下一轮自动重置,不会永久堵住发送;
- 请示失败(如内容为空、登记不上)不暂停 —— 不白白卡住任务;
- 号主的答复(不管从哪个入口来)作为新消息回到会话,agent 从 checkpoint 恢复继续推进。

同一问题重复请示会幂等去重,不会刷屏。

对应的回归测试在 `tests/test_hitl.py`(13 例:默认开 / 可开关 / 两变体的底线都在 /
配置真的改变了模型收到的提示词 / 请示后不发送、不记历史 / 下一轮不被残留挡住)。

## 6. 长期记忆:攒批写入

长期记忆**不再逐条写入** —— 那会把记忆碎成一堆"嗯""好的"。

- 只有 `monitor=1` 的会话参与;
- 触发条件:待处理消息数 ≥ `digest_max_messages`(20) 或 消息静止超过 `digest_window_seconds`(1800);
- 调度器每 60 秒扫一次,把该总结的会话各总结一轮(fast 模型);
- **值得记才写**:模型认为这批没价值就一条不写,但处理水位线照常推进;
- 进度存在 `memory_batches` 表(游标 + 水位线),服务重启不丢。

### 6.1 读回来: 检索的现实(踩过的坑)

写进去不代表读得回来。Doppel 的 SQLite 检索是**字面子串匹配**
(FTS 短语 AND,失败回落 `LIKE '%整串%'`),而调用方给的是**对方刚说的整句话**——
"明天组会几点?"永远不可能恰好是某条记忆的子串,于是**检索恒为空**,
而且失败是静默的(空列表 = "没有记忆")。

适配层([app/memory.py](../app/memory.py))因此做了两件事:

1. **拆词多查再合并**: 整句先试,再按"二字片段优先、三字次之"的顺序
   拆出片段分别检索(中文实词以二字为主: 组会/明天/课表),
   让实词能命中;命中即停,检索是本地 SQLite 查询,不花钱。
   跨词边界的碎片("的组""午了")会被过滤,但**过滤集刻意收得很窄** ——
   砍"会"会连"组会/开会"一起砍,漏掉实词等于那条记忆永远找不回来。
2. **最近记忆兜底**: 拆词仍无命中时,取该 scope 最近的记忆 ——
   同一会话最近的记忆本来就跟当前话题最相关,总好过一条都不给。

提示词里每条记忆都带**说话人 + 本地时间**(`[对方 2026-09-22T21:50]`),
便于处理"事实会过期"的场景(如课表变更)。

**没做的**: 语义检索(向量)。Doppel 0.8.x 提供了 `SemanticIndex` /
`TemporalSemanticIndex` / reranker 等宿主接口,但要宿主自己接一个向量后端
(embedding API 或 pgvector),会引入每轮的 embedding 调用成本。
目前用拆词 + 兜底顶着 —— 效果是"能命中实词",而不是"理解语义"。

### 6.2 事实会过期、说法会矛盾: 整理环节

"km 每周三晚上有课" → 后来"课表改到周五了"。旧事实如果还留在库里,
检索照样会把它捞出来 —— **agent 会拿着过期信息去回话**。
两条互相矛盾的说法(自己说周三有空、对方说周三没空)同时存在也一样。

[app/consolidation.py](../app/consolidation.py) 用 Doppel 的
`ConsolidationRunner` + 确定性整理器(**零模型成本**)每轮整理一遍:

| 情况 | 处理 |
|---|---|
| 同一槽位上一模一样的说法 | `merge` 合并成一条 |
| 新说法带**明确订正标记**(聊天里说了"改了/取消了") | `correct`: 旧说法置为 `superseded`,**不再被检索出来** |
| 说法矛盾、又没有订正证据 | `conflict`: 保留双方 + 写冲突标记 + **报给号主确认** |

三条刻意的设计:

- **不猜**: 没有明确订正证据时绝不覆盖旧说法 —— 猜错就是替号主改口供。
  冲突走上报队列的 `question` 通道问人(与 HITL 请示同一条出口),
  号主答复后新一轮整理会看到新的说法并收敛;
- **槽位是字符串精确匹配的**: 同一件事这批评成"课表"、下批评成"课程安排",
  就永远不会被比对。所以总结提示词里会带上**该会话已有的槽位名**让模型复用
  (见 `known_topic_keys`),槽位名归一化只做大小写/空白/标点处理,不做同义归并;
- **冲突标记不进提示词**: 它是给整理/通知环节看的记录(内容是英文的
  "Unresolved ... conflict in topic X"),混进记忆块只会让模型以为号主在说胡话。
  冲突本身已经报给号主了。

宿主责任(Doppel 明确留给宿主的三件事)都落在这一层:
调度(每 30 分钟一个会话最多整理一次)、检查点持久化(`memory_consolidation` 表)、
单写者(只在调度器里跑)。

前提: 记忆必须带 `personal-memory` 标签 —— 整理器只读带这个标签的记录,
少了它记忆就永远不参与整理。写入时由总结器一并打上
(连同 `topic_key` / `revision_kind` / `temporal_status` / `personal_memory_type`)。

## 7. 工具权限

每个会话能用哪些工具由策略决定,**两层拦截**:

1. `reason` 只把授权工具 bind 给模型(未授权的模型根本看不到);
2. `act` 拒绝执行未授权的调用并写审计(防模型幻觉或历史残留);
3. 高危工具内部再校验一次(`send_qq_message` 有 `high_risk` 标签)。

默认集:

- **私聊**:全部工具;
- **群聊**:不给 `send_qq_message`(群聊人数多、不可控,被诱导替号主发消息的风险最高)。
  需要时用 `allowed_tools: ["send_qq_message"]` 显式授权。

新工具只要打上 `high_risk` 标签(`tool.tags = [HIGH_RISK_TAG]`),群聊默认就会被拦下。

## 8. 成本

| 环节 | 模型调用 |
|---|---|
| 未监视的会话 | 0 |
| 监视落库 | 0 |
| 上报: 信号提取 + 事件判定 + 上下文 | **0**(纯字符串/本地查询) |
| 上报: 快模型复核 | 每批候选 1 次 fast(可关,日配额封顶) |
| 攒批记忆总结 | 每批 1 次 fast |
| 记忆整理(过期/冲突) | **0**(确定性整理器,本地计算) |
| 自动回复 | 每条消息 1 次主模型(仅 `reply_mode=auto`) |

此外,checkpoint 历史会按 `history_max_messages` 裁剪(保留最近窗口,
不动数据库里的完整历史),避免长会话的 prompt 无界增长。

## 9. 运维与排障

### 9.1 冒烟: 验证两条"只跑过假模型"的路径

攒批记忆与上报复核都依赖模型的 JSON 输出。单元测试用假模型只能验证接线,
验证不了"提示词在真模型上产不产得出能解析的东西"。**它们的失效都是静默的**:
攒批解析失败时业务上等同于"这批没值得记的",水位线照常推进,那批消息再也不会被总结。

```powershell
uv run python scripts/smoke_llm_paths.py
```

它用**生产代码本身**真调一次模型,输出每项的 PASS/FAIL 与模型原始结果,
不碰数据库、不发任何消息。**改动这两个提示词后请跑一次**(提示词一改,
真模型上的输出格式就可能变)。

### 9.2 健康度接口: 看"有没有静默的记忆缺失"

```http
GET /api/memory/health
```

返回:

| 字段 | 含义 |
|---|---|
| `enabled` / `init_error` | 记忆功能是否启用、初始化失败原因 |
| `summary.calls` | 总结器调用次数 |
| `summary.empty` | 模型判定"没值得记的"(正常) |
| `summary.unparsed` | **有输出但解析不出**(可疑 —— 提示词或模型出问题) |
| `summary.last_unparsed_sample` | 上一次解析失败的原始输出(排查用) |
| `batches[]` | 各会话的待处理条数、上次状态与错误 |

关注 `unparsed` 与 `batches[].pending_count` 一直涨的会话。

### 9.3 存储: 别让库悄悄涨满

监视中的群聊会持续写入 —— 不设上界,迟早把磁盘啃满(而且是**静默地**啃)。
默认开启保留策略,规则见下。删数据不可逆,所以设计原则是**宁可不删,不可误删**。

```powershell
# 看存储占用与行数
uv run python scripts/retention.py stats

# 预览会删什么(默认只看不删)
uv run python scripts/retention.py plan

# 真正执行(一般不用手动跑: 服务每 24 小时自动清理一次)
uv run python scripts/retention.py apply
```

默认保留期(都可用环境变量调整,设 0 = 永久保留):

| 对象 | 默认 | 额外保护 |
|---|---|---|
| 消息 | 90 天 | **只在已总结进长期记忆之后才可能删**;每会话保底留最近 200 条;有进行中目标的会话整个跳过 |
| 事件审计 | 30 天 | —— |
| 调度记录 | 30 天 | 只删已结束的(done/failed/expired/busy),没跑完的不动 |
| 定时唤醒 | 30 天 | 只删已触发/已取消的,**pending 永不删** |
| 上报记录 | 30 天 | 只删已处理完的(acked/dropped/dead),待消费的不动 |
| checkpoint | 30 天 | 只对**休眠**会话保留最新一份(不是删会话),正在聊的不动 |

**最关键的一条**: 消息的保护规则一 ——
攒批总结读的正是 messages 表,删掉还没总结的消息等于那段内容**永久消失**
(记忆和原始记录同时没了)。判定依据是会话的攒批水位线:
**没有水位线(从未总结过)就一条都不删**。

`GET /api/storage` 随时可查占用;`GET /api/storage?plan=true` 预览清理计划(只读)。
