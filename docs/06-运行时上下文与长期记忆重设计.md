# 运行时上下文与长期记忆重设计

> 状态：设计草案（v0.1）
> 本文档以**当前代码实现为准**，03/04/05 等早期文档仅作历史参考，描述与本设计冲突时以本文档 + 代码为准。

## 1. 背景与目标

Memo Echo 作为代理 QQ 账号的社交 Agent，同时面对多个联系人/群。核心矛盾是：

- **隔离**：每个会话的上下文必须相互独立，绝不能把 A 私聊的内容串到 B 私聊（防串台）。
- **流通**：复杂任务（父工作流）需要跨会话传递信息，如"问 km 几点上课，再转告小号"。
- **连贯**：Agent 要像号主本人——记得"跟谁发生过什么、跟谁用什么风格"，长期记忆是"像号主"的关键。
- **溯源**：前期已区分"Agent 代发"与"号主本人发送"（actorType / factAuthority），该机制必须保留并强化，防止 Agent 把自己的输出当成号主事实。

本设计重写两部分：

1. **运行时上下文**：一次执行内模型"看见什么"，定义隔离边界与跨会话流通的合法通道。
2. **长期记忆**：跨会话"记住什么、怎么检索、怎么确认"，引入时间感知 + 语义检索。

## 2. 现状盘点（以代码为准）

### 2.1 已落地且保留

| 能力 | 代码位置 | 说明 |
| --- | --- | --- |
| 会话作用域 | `UnifiedEvent.scope`（Java event-record） | `userId + platform + chatType + chatId` 为第一性隔离键 |
| 委托任务上下文组装 | `app/services/delegated_task_context.py` `DelegatedTaskContextAssembler` | 组装 scope/taskTimeline/preTaskHistory/workflowFacts 等 |
| 模型上下文投影 | `build_model_context` | 投影 taskGoal/successCriteria/conversationTimeline/workingMemory/actionLedger/workflowFacts |
| 跨步骤事实 | `workflowFacts`（P3 落地） | 步骤 A 确认事实以结构化键值注入下游步骤，不传原始消息 |
| 身份溯源 | `actorType`（OWNER/CONTACT/AGENT/SYSTEM） | 每条事件标记真实来源 |
| 事实权威 | `factAuthority`（human_self/peer_statement/agent_output/derived_summary） | Prompt 明确 agent_output 不能作为现实证据 |
| 记忆三态闭环 | `memory_candidate` 表 + `MemoryCandidateExtractor` + `MemoryManager` | CANDIDATE → VERIFIED/REJECTED → EXPIRED；只取 VERIFIED 未过期 |
| 记忆审计 | `executionTrace.verifiedMemoryIds` | 记录每次实际注入的记忆 ID |
| 上下文压缩 | `app/memory/context_compressor.py` | 预算内原文，超限用"较早派生摘录+最近原文"，DERIVED_SUMMARY 低权威 |
| 会话认知卡表 | `conversation_cognition_card`（Java） | M1 认知卡存储基础（主控台链路未接） |

### 2.2 短板（本设计要解决的）

- 记忆无**时间维度**：不知道"约过、已过期、下周三到期"，无法回答"上次/后来/最近"。
- 无**语义检索**：只靠作用域精确过滤，无法按主题/关系召回。
- 无**事件记忆**：只有"事实"，没有"发生了什么"的事件流。
- 无**关系记忆**：不记录"谁与谁是什么关系"（同学/老师/买家），这是跨会话流通的基石。
- 风格记忆未实现（本设计暂缓，见 §7）。
- 运行时上下文每轮重建、无持久化工作记忆（M1 摘要未参与主链路）。

## 3. 核心原则

1. **原始消息严格按会话隔离**；跨会话只流通"已验证事实 + 来源"，不流通原始文本。
2. **上下文是数据包，不是 Prompt**：带来源、时间、作用域、版本号，任何结论可回溯。
3. **Agent 代发 ≠ 号主本人**：actorType/factAuthority 贯穿写入、检索、注入、审查全链路。
4. **长期记忆 = 时间 + 关系 + 语义**：能回答"何时发生、对谁、主题相关"。
5. **自动记忆不直接成为强事实**：自动提取的内容进候选，用户确认后才可作高可信证据（双闭环）。
6. **降级不阻断**：记忆/图谱不可用时，Agent 退回无记忆继续回复。

## 4. 目标架构总览

```
┌───────────────────────────── 长期记忆层 ─────────────────────────────┐
│                                                                      │
│  [Graphiti / Neo4j] 自动记忆层（Python 侧）                           │
│   ├─ Episode    : 原始事件/消息（含 actorType、发生时间）              │
│   ├─ Entity     : 人/群/地点/主题（含 group_id 隔离）                  │
│   └─ Relationship: 实体间事实（双时间轴 valid_at/invalid_at）          │
│         ▲ 提取（LLM，DeepSeek 兼容 OpenAI） │ 检索（语义+时间+group）   │
│         │                                   ▼                        │
│  [MySQL memory_candidate] 确认层（Java 侧，保留现有闭环）              │
│   └─ CANDIDATE → VERIFIED/REJECTED → EXPIRED（用户确认才生效）        │
│         ▲ 强事实候选回写                             │ 仅返回 VERIFIED │
└─────────┼──────────────────────────────────────────────┼────────────┘
          │                                               │
┌─────────▼────────────────── 运行时上下文 ───────────────▼────────────┐
│  DelegatedTaskContextAssembler / build_model_context                 │
│  ┌────────────────────────────────────────────────────────────┐      │
│  │ ContextEnvelope（一次执行）                                 │      │
│  │  scope(隔离) · timeline(带actorType) · workflowFacts        │      │
│  │  verifiedMemories(确认层) · graphMemories(图谱检索)          │      │
│  │  taskState · profiles · guardrails(timelineVersion)         │      │
│  └────────────────────────────────────────────────────────────┘      │
│      模型投影（只暴露当前会话原文 + 跨会话"事实+来源"）                │
└──────────────────────────────────────────────────────────────────────┘
```

两个记忆层职责分离：

| | Graphiti 自动层 | MySQL 确认层 |
| --- | --- | --- |
| 内容 | 事件、实体、关系、主题语义 | 高可信事实、用户确认后的持久偏好 |
| 时间 | 双时间轴（valid_at/invalid_at） | 单 expires_at |
| 检索 | 语义向量 + 时间过滤 + group 隔离 | 作用域精确过滤 |
| 写入 | Runtime 自动，事件驱动 | Runtime 提交候选 + 用户/桌面确认 |
| 权威 | 低（自动，仅作线索） | 高（VERIFIED 才进 Prompt） |
| 审计 | 检索返回带 source（Episode 引用） | `verifiedMemoryIds` |

## 5. 技术选型：Graphiti + Neo4j

### 5.1 选型理由

- **时间感知**：双时间轴（valid_at/invalid_at）原生支持"约定 8 月 23 日上课、下周三到期"这类时间敏感事实。
- **关系/事件一体**：Episode→Entity/Relationship 的自动增量提取，正好覆盖"跟谁发生了什么、谁和谁什么关系"。
- **语义检索 + 时间过滤**：召回"最近关于上课时间的事实"而非全量注入。
- **group_id 隔离**：Neo4j 上按组隔离命名空间，天然对应我们的会话/作用域隔离。
- 官方提供 LangChain 集成，与现有 langgraph 栈兼容（langchain-core 0.3）。

### 5.2 落地约束（已确认）

- **部署**：Neo4j 用 Docker Desktop 运行（docker-compose），本机测试形态；生产同形态。
- **语言边界**：Graphiti 是 Python 库，只运行在 agent-runtime；Java event-center 不直接接触图谱，事实统一经 Runtime。
- **LLM 依赖**：Graphiti 自动提取实体/关系需调用 LLM（OpenAIClient 兼容协议），本项目用 DeepSeek（OpenAI 兼容，base_url 可配置）。**注意配额**：每次 Episode 提取都是一次 LLM 调用，需要节流（见 §8 分期）。
- **Embedding**：自定义本地 embedder（fastembed 已依赖，bge-small-zh），不依赖外网。
- **待验证**：
  - Graphiti 与 langchain-core 0.3 集成版本兼容性（graphiti 要求 langchain>=0.3，需实测）。
  - 自定义 Embedder 接口签名（`Embedder.embed_texts/embed_query`）。
  - 中文本地 embedding 的检索质量（bge-small-zh 维度 512）。

### 5.3 图谱数据模型（映射）

| Graphiti 概念 | 本项目映射 |
| --- | --- |
| `group_id` | `scope` 派生键：`userId:platform:chatType:chatId`（会话级）或 `userId`（全局级） |
| `Episode` | 一条归一化事件（含 actorType、factAuthority、occurredAt 注入 content 前缀） |
| `Entity` | 联系人、群、地点、主题、账号本人（本人实体标记 OWNER） |
| `Relationship` | 实体间事实（"km 是 同学"、"上课时间是 9 点"），带 valid_at/invalid_at、来源 Episode |

## 6. 长期记忆双闭环设计

### 6.1 写入链路

```
事件进入 Event Center (Java)
  → Runtime 消费统一事件
    → ① 判 actorType：仅 OWNER/CONTACT 的文本事件进图谱；AGENT 代发仅标记，不提升可信
    → ② 有授权 + 未达节流 → Graphiti.add_episode(name, content, valid_at, group_id, source)
         → 自动提取 Entity/Relationship（CANDIDATE 级）
    → ③ 若提取出"强事实"（本人明确陈述、时间/地点/关系类）
         → 复用现有 MemoryCandidateExtractor 路径提交 CANDIDATE 到 MySQL
    → ④ 用户确认 → VERIFIED（现有闭环不动）
    → ⑤ VERIFIED 的 key 事实回写图谱（把自动边升级为 confirmed 边）
```

关键规则：
- **AGENT 代发内容**可进 Episode 维持连贯，但提取时标记 `factAuthority=agent_output`，不生成 CANDIDATE、不提升可信。
- **CONTACT 单方面陈述**只作为低可信候选，不自动确认。
- **事件级节流**：同一会话的 Episode 按消息数/时间合并（如每 N 条或每轮对话一个 Episode），控制 LLM 提取调用量。

### 6.2 检索链路

```
一次执行开始（L0）
  → Runtime 确定 scope
    → ① MySQL 确认层：MemoryManager.build_verified_memories(event)
         （现有逻辑不动，只返回 VERIFIED 未过期）
    → ② Graphiti 检索：graphiti.search(query, group_ids=[会话级, 全局级], valid_at=now)
         → 结果带来源 Episode 引用，按相关度 + 时间过滤
    → ③ 组装进 ContextEnvelope.graphMemories / verifiedMemories
    → ④ 注入模型（带 memoryId/source 引用）+ 写入 executionTrace 审计
  → Graphiti 不可用 → 降级：仅 MySQL 确认层，基础聊天不阻断
```

检索触发点（不默认全量注入）：
- 初始化会话上下文（认知卡）
- 用户提到"上次/后来/还记得/还是老地方"等回顾意图
- 委托任务创建/执行时（检索该联系人与任务相关事实）
- Review Agent 审查时（要求对声称的事实提供记忆来源）

## 7. 运行时上下文设计（隔离与流通边界）

### 7.1 模型可见内容（一次执行）

| 字段 | 内容 | 跨会话边界 |
| --- | --- | --- |
| `scope` | 当前会话四元组 | 只本会话 |
| `timeline` | 本会话原始消息（带 actorType/factAuthority） | 只本会话 |
| `preTaskHistory` | 任务前本会话窗口 | 只本会话 |
| `workflowFacts` | 父工作流已验证事实（键值 + 来源） | **允许跨会话** |
| `verifiedMemories` | 本用户 VERIFIED 记忆 | 本用户，按 scope 过滤 |
| `graphMemories` | 图谱检索结果（实体/关系/事件摘要） | 按 group_id 过滤，跨会话只给"事实+来源" |
| `taskState` | 任务目标/步骤/待确认 | 本工作流 |
| `guardrails` | 权限、timelineVersion | 本执行 |

### 7.2 三条铁律

1. **原始消息零跨会话**：任何会话的原文（含图片/文件引用）绝不注入到另一会话的模型上下文。
2. **跨会话只走"事实"**：父工作流把"已确认事实"写入 `workflowFacts`，下游步骤只看到事实 + sourceEventIds，看不到产生它的会话原文。例：
   ```text
   ✅ workflowFacts: km_available_time = "九点" (source: evt-xxx, confirmed_by: OWNER)
   ❌ 注入 km 会话原文"我今晚七点有课吗"
   ```
3. **图谱检索跨会话同样受限**：`group_ids` 只含当前会话 + 全局层；需要联系人关系时可查"该联系人的关系记忆"，但原文仍不可见。

### 7.3 与现有机制的衔接

- `DelegatedTaskContextAssembler` 增加 `graph_memories` 装配步骤（检索失败 → 空列表 + 降级日志）。
- `build_model_context` 增加 `graph_memories` 投影，提示词注明：图谱记忆为**自动提取的低权威线索**，需要现实事实必须回查确认层或原文。
- `MemoryManager` 扩展为"确认层 + 图谱层"两个数据源，保留现有接口签名（`build_verified_memories` 不变，新增 `build_graph_memories`）。
- 现有 `context_compressor` 压缩逻辑继续作用于 `timeline`，图谱检索结果单独预算。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| Neo4j 本机资源/运维负担 | Docker Compose 一键起停；社区版单实例足够 |
| Graphiti 每次 Episode 提取消耗 LLM 配额（本项目曾 402） | Episode 按会话节流合并；提取失败降级；LLM 客户端可配置 |
| 自动提取的低权威内容被当强事实 | 双闭环：自动只作线索，确认后才进高可信 Prompt；提示词标注权威 |
| 本地 bge-small-zh 检索质量不足 | P-D 评估，可换多语言/更大本地模型，embedder 可配置 |
| Graphiti/langchain 版本兼容 | P-A 先做最小 Demo 消解待验证项，再铺开 |
| 图谱数据与 MySQL 事实漂移 | 图谱只读线索 + 确认层为权威；回写仅单向（确认→升级边） |
