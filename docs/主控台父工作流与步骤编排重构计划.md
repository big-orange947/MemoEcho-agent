# 主控台父工作流与步骤编排重构计划

## 1. 重构目标

主控台接收的是一条用户命令，但一条命令可能包含多个联系人、多个阶段和前后依赖。当前实现把命令按联系人复制为多个互相隔离的委托任务，无法表达“先询问 A，拿到结果后再转告 B”，也无法在重启后恢复完整任务进度。

本次重构把主控台委托升级为两层模型：

- `DelegatedWorkflow`：承载用户原始命令、执行计划、共享事实和整体状态。
- `DelegatedTask`：降级为工作流中的一个可执行步骤，只绑定一个会话并完成一个明确动作。

核心原则：模型负责理解、规划和选择工具，确定性执行器负责依赖、状态迁移、幂等、权限和恢复。

## 2. 本阶段范围

### 2.1 必须完成

1. 一条主控台命令只创建一个父工作流。
2. 父工作流包含有向无环的步骤依赖。
3. 只有依赖已满足的根步骤可以启动。
4. 步骤结果写入工作流共享事实，后继步骤通过事实引用消费结果。
5. 同一工作流内允许串行、并行和汇合。
6. 工作流和步骤均持久化到 MySQL，服务重启后可以恢复。
7. 创建、启动、推进和完成必须具备幂等键，避免消息重投产生重复任务或重复发送。
8. 客户端按父工作流展示，不再把同一命令衍生的步骤显示成互不相关的任务卡片。

### 2.2 暂缓实现

- 文档、压缩包、表格和图片文件的具体解析。
- 大规模 Subagent 和 MapReduce 执行。
- 跨设备分布式执行器。

本阶段只为文件任务预留 `workflowType`、`stepRole` 和事实载荷字段，不实现文件工具。

## 3. 目标执行范式

### 3.1 Direct

不需要持续状态的只读请求直接返回结果，不创建委托工作流。

### 3.2 ReAct

单会话、目标明确、可以边观察边调用工具的任务使用 ReAct。例如“问 km 今晚是否有空”。

### 3.3 Plan and Execute

存在多个联系人或明确依赖时，Router/Planner 先生成步骤图，再由执行器逐步推进。例如：

```text
询问 km 晚上几点上课
  -> 等待 km 回复
  -> 提取 class_time
  -> 将 class_time 转告给小号
  -> 完成并汇报
```

### 3.4 后续扩展

复杂文件任务可在一个步骤内部使用 Subagent；批量独立处理可使用 MapReduce。它们不能绕过父工作流状态机和权限层。

## 4. 数据模型

### 4.1 delegated_workflow

| 字段 | 作用 |
| --- | --- |
| id | 父工作流 ID |
| user_id | 所属用户 |
| source_execution_id | 主控台单次命令执行 ID，作为幂等键 |
| original_command | 原始用户命令 |
| title | 面向用户的简短标题 |
| workflow_type | REACT / PLAN_EXECUTE / SUBAGENT / MAP_REDUCE |
| status | PLANNING / RUNNING / WAITING_EXTERNAL / REPLANNING / COMPLETED / FAILED / CANCELLED |
| plan_json | Planner 原始结构化计划 |
| facts_json | 共享事实黑板 |
| progress_summary | 当前自然语言进度 |
| failure_reason | 失败原因 |
| created_at / updated_at / completed_at | 生命周期时间 |

### 4.2 delegated_task 扩展

`delegated_task` 继续承担单会话步骤执行，但新增：

| 字段 | 作用 |
| --- | --- |
| workflow_id | 所属父工作流 |
| step_key | 工作流内稳定步骤标识 |
| step_order | UI 和调试排序 |
| step_role | ASK / RELAY / NOTIFY / COLLECT / AGGREGATE / ACTION |
| step_instruction | 该步骤的最小职责，不再保存整条命令副本作为执行指令 |
| depends_on_json | 前置 step_key 列表 |
| result_json | 步骤输出和提取事实 |

步骤状态使用：

- `BLOCKED`：依赖未满足。
- `ACTIVE`：可以执行或正在执行。
- `WAITING_EXTERNAL`：已发送消息，等待目标会话新事件。
- `COMPLETED`、`FAILED`、`CANCELLED`：终态。

## 5. 上下文与事实边界

### 5.1 私有会话上下文

每个步骤只能读取自身绑定会话中、任务开始后的消息，并明确标注：

- `SELF`：用户本人或 Agent 代用户发送。
- `PEER`：对方发送。
- 时间戳、消息 ID、是否由 Agent 发送。

不同会话的原始聊天内容不能直接互相注入，避免把用户给 A 的备注或对话泄露给 B。

### 5.2 工作流共享事实

跨步骤只传递经过提取的结构化事实，例如：

```json
{
  "class_time": {
    "value": "今晚 19:00",
    "sourceStep": "ask_km",
    "sourceEventId": "qq-message-id",
    "confidence": 0.97
  }
}
```

后继步骤引用 `facts.class_time.value`，而不是读取 km 的完整私聊记录。

## 6. Planner 输出契约

Planner 必须返回完整计划，不再只返回联系人数组：

```json
{
  "title": "询问上课时间并转告小号",
  "workflowType": "PLAN_EXECUTE",
  "steps": [
    {
      "stepKey": "ask_km",
      "order": 1,
      "role": "ASK",
      "instruction": "询问 km 今晚几点上课",
      "dependsOn": [],
      "target": {"platform": "qq", "chatType": "private", "chatId": "..."},
      "successCriteria": "获得明确上课时间",
      "produces": ["class_time"]
    },
    {
      "stepKey": "relay_to_xiaohao",
      "order": 2,
      "role": "RELAY",
      "instruction": "把 class_time 转告给小号",
      "dependsOn": ["ask_km"],
      "target": {"platform": "qq", "chatType": "private", "chatId": "..."},
      "requiresFacts": ["class_time"],
      "successCriteria": "消息发送成功"
    }
  ]
}
```

Java 侧必须重新校验所有目标会话均属于当前用户授权范围，并校验依赖引用、stepKey 唯一性和 DAG 无环。

## 7. 确定性执行规则

1. 创建工作流时事务性写入父工作流和全部步骤。
2. 无依赖步骤写为 `ACTIVE`，有依赖步骤写为 `BLOCKED`。
3. `ACTIVE` 步骤通过现有事件和 Runtime 链路执行。
4. 步骤完成时写入 `result_json`，将可公开结果合并到 `facts_json`。
5. 执行器扫描直接后继步骤；仅当全部依赖完成且所需事实存在时，将其原子更新为 `ACTIVE`。
6. 若仍有执行中步骤，父工作流保持 `RUNNING`；只有等待外部回复时为 `WAITING_EXTERNAL`。
7. 全部必要步骤完成后，父工作流进入 `COMPLETED` 并生成汇报。
8. 是否结束由 Agent 通过结束步骤工具作出语义判断，但状态写入和合法性校验由 Java 完成。

## 8. 幂等与并发

- 父工作流唯一键：`user_id + source_execution_id`。
- 步骤唯一键：`workflow_id + step_key`。
- 事件租约继续使用现有 claim/complete 机制。
- 发送消息工具必须携带 `workflow_id + step_key + action_id`，作为出站幂等键。
- 激活后继步骤使用条件更新：只有 `BLOCKED` 可以变成 `ACTIVE`。
- 重复完成同一步骤返回已保存结果，不重复合并事实和启动后继步骤。

## 9. UI 目标

主控台展示一张父任务卡片：

- 标题、原始目标、整体状态和自然语言进度。
- 子步骤时间线，展示依赖关系、联系人、等待原因和结果。
- 串行步骤在时间线上纵向连接；并行分支在同一层展示。
- 只允许在父工作流层执行暂停、取消和查看汇报；步骤详情用于诊断，不鼓励用户逐个管理。

## 10. 实施顺序

1. 新增父工作流表和步骤扩展迁移。
2. 新增 Java 工作流模型、Repository、事务创建服务和只读接口。
3. 新增 Python `WorkflowPlan` / `WorkflowStepPlan` 契约。
4. 替换 Router 的联系人列表输出，删除按联系人复制任务循环。
5. 只启动根步骤，并接入步骤完成后的事实写入和后继激活。
6. 改造客户端父卡片和步骤时间线。
7. 增加闭环测试：串行转告、并行通知、汇合、重复事件、服务重启和取消。
8. 删除不再被调用的旧解析和兼容入口。

## 11. 验收场景

### 串行转告

“帮我询问 km 晚上什么时候上课，然后转告给小号”只能先联系 km；收到明确回复后才联系小号。

### 并行通知

“通知 km 和小号今晚有课”同时生成两个无依赖通知步骤，并分别发送一次。

### 并行收集并汇总

“分别问 km 和小号今晚是否有空，再告诉我结果”并行询问，等待两个结果后执行汇总步骤。

### 恢复与幂等

服务在任意步骤重启后，任务不丢失、不重复创建、不重复发送，并能从数据库继续推进。
